# OTA / bootloader protocol (types 6 and 7)

Same framing as types 1-5: raw packet = `[version=1][type]...[crc16 LE]`,
CRC-16/CCITT-FALSE over everything before the CRC, then COBS + `0x00`.
Works identically over BLE NUS and USB-CDC. Types 1-5 are unchanged.
Golden vectors (secret, nonce, image, every packet as raw+wire hex):
`OTA_VECTORS.json`, generated by `ota_ref.py` (the normative encoder).
All integers little-endian. Responses go only to the link that sent the command.

## Packets
`OTA_CMD  (6, host->dev): [1][6][op][payload][crc]`
`OTA_RESP (7, dev->host): [1][7][op][status][payload][crc]`   (op echoes the command)

| op | name | cmd payload | OK response payload |
|---|---|---|---|
| 1 | HELLO | - | `[caps=1 u8][max_chunk u16 = 192][slot_size u32][nonce 16]` fresh `esp_random` nonce, replaces any previous one |
| 2 | BEGIN | `[size u32][sha256 32][mac 32]` | - |
| 3 | CHUNK | `[offset u32][data 1..192]` | `[next_offset u32]` |
| 4 | END | - | - (device reboots ~300 ms after sending it) |
| 5 | ABORT | - | - |
| 6 | BOOTLOADER | `[mac 32]` | - (device reboots into ROM download mode ~200 ms later) |

`mac(BEGIN) = HMAC-SHA256(secret, "OTA-BEGIN" || nonce || size_le32 || sha256)`
`mac(BOOTLOADER) = HMAC-SHA256(secret, "OTA-DL" || nonce)`
`secret` = 32 bytes, set at firmware build (`-DLAB_OTA_SECRET_HEX="\"<64 hex>\""`
in build_opt.h, never committed) and typed into the app. No secret compiled in
=> every op except ABORT answers `DISABLED`. A nonce is single use (consumed by
a BEGIN or BOOTLOADER attempt, good or bad); compare MACs in constant time.

## Status
0 OK, 1 BAD_STATE, 2 BAD_LENGTH, 3 DISABLED, 4 BAD_MAC, 5 TOO_BIG (size > slot),
6 BAD_HASH, 7 BAD_OFFSET (payload = `[next_offset u32]` so host can resync),
8 FLASH_ERROR.

## Device state machine
IDLE -HELLO-> NONCE -BEGIN(ok)-> RECEIVING -END(ok)-> reboot.
ABORT, a bad BEGIN, 30 s without a valid packet, or link loss -> IDLE (partial
write discarded, `esp_ota_abort`). CHUNK is accepted only in RECEIVING and only
if `offset == next_offset`; a repeat of the immediately previous chunk (lost
ACK) is re-ACKed without rewriting; anything else -> BAD_OFFSET. Chunk data is
streamed into the inactive OTA slot (`esp_ota_*`) while feeding an incremental
SHA-256. END requires `next_offset == size` and digest == BEGIN's sha256, then
`esp_ota_end` + `esp_ota_set_boot_partition`. RMT RX is suspended from BEGIN
until the session ends. Stop-and-wait: host sends one packet, waits for its
response (timeout 2 s; a packet is sent at most 3 times in total; BEGIN is never retried because it consumes the nonce).

## Safety
* Two 2 MB slots (`PartitionScheme=no_fs`). The running slot is never written.
* The prebuilt bootloader has app rollback enabled: the new image boots as
  PENDING_VERIFY and reverts on reset unless the app calls
  `esp_ota_mark_app_valid_cancel_rollback()`; firmware does so once ~10 s of
  loop() have run with BLE up.
* OTA/BOOTLOADER ops are rejected unless authenticated by the MAC; image
  integrity = SHA-256 from BEGIN (the MAC covers it).
* Does not provide image *signing*: anyone holding the secret can flash anything.

## Buffer implications (firmware)
Largest inbound raw packet = 201 B (CHUNK), wire 203 B. Parser buffers
(`RX_BUFFER_MAX`, `RX_DECODED_MAX`) must grow to >= 256 without changing
behaviour of types 3/4/text. HWCDC RX queue defaults to 256 B: call
`Serial.setRxBufferSize(1024)` before `Serial.begin`.

## Bootloader flag caveat
`BOOTLOADER` sets RTC_CNTL_FORCE_DOWNLOAD_BOOT (RTC_CNTL_OPTION1_REG = 0x600080F4
on ESP32-C3), which survives resets. The app clears it at boot, but a chip
flashed while the flag is set would reboot into the ROM downloader again. So
flash with the register cleared first: `esptool --chip esp32c3 write-reg
0x600080F4 0` and then `write-flash ...` in the same download session
(unverified on hardware; a power cycle also clears it).
